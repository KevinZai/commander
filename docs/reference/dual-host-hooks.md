# Dual-host hook contract (Claude Code + Codex)

One set of Node hook scripts and one `hooks/hooks.json` serve both hosts. This page records the contract and the one-time Codex trust step. Platform facts: [platform-facts-2026-10.md](platform-facts-2026-10.md) (Claude Code hooks and the Codex section).

## Contract

| Item | Rule |
|---|---|
| Source of truth | `commander/cowork-plugin/hooks/hooks.json` and `hooks/**`. The Codex copy under `commander/cowork-plugin-codex/` (`hooks.json` at its root, scripts under `hooks/`) is generated by `npm run build:codex`; never hand-edit it. |
| Command form | Quoted shell form: `node "${CLAUDE_PLUGIN_ROOT}/hooks/x.js"`. Codex has no `args` exec form, and Desktop installs sit under a path with a space, so the quotes are required. |
| Plugin root | Codex sets `PLUGIN_ROOT` and `PLUGIN_DATA`, plus `CLAUDE_PLUGIN_ROOT` / `CLAUDE_PLUGIN_DATA` as compatibility aliases. Claude Code sets only the `CLAUDE_*` pair. `${CLAUDE_PLUGIN_ROOT}` therefore resolves on both hosts and is never rewritten. |
| Manifest | `.codex-plugin/plugin.json` declares `"hooks": "./hooks.json"`; the Claude plugin loads `hooks/hooks.json` by convention. |
| Events | Codex supports a subset of Claude Code's events. Claude-only events are dropped from the mirror (`commander/adapters/codex/hook-event-map.json`). |
| Handler fields | Codex has no `args`, `onFailure`, `if` or `once`, and skips `async` handlers. Translation strips `async` and clamps the timeout so the handler still runs, synchronously. |
| Output | Use fields both hosts accept: `continue`, `suppressOutput`, `systemMessage`, `hookSpecificOutput.additionalContext` on UserPromptSubmit, and top-level `decision: "block"` + `reason` on Stop. |
| Host detection | A hook that must behave differently branches on `PLUGIN_ROOT` (set = Codex) or the mirror path. The routing hook uses `detectHost()` in `hooks/lib/route-scorer.mjs`; `CCC_SOURCE_APP=codex\|claude-code` overrides it. |
| Menus | The routing hook (`intent-classifier.js`) asks Claude Code for `AskUserQuestion` (up to 4 options, 🟢 first) and Codex for `request_user_input` (up to 3 options, "(Recommended)" first) with `$ccc-*` names. `CCC_ROUTE_MENU=list` asks for a numbered list on either host. |

A new hook is dual-host if it uses the quoted command form, reads only the common input fields (`session_id`, `cwd`, `hook_event_name`, `transcript_path`), emits only the output fields above, and branches on the host for anything host-specific. `commander/tests/dual-host-hooks.test.js` checks this contract for the routing hook.

## Codex one-time hook trust

Installing or enabling the plugin does not trust its hooks. Codex skips plugin-bundled hooks until the user reviews and trusts the current hook definition. No adapter can bypass this, and Commander does not try to.

Onboarding steps for Codex users:

1. Install: `codex plugin marketplace add KevinZai/commander`, then `codex plugin add commander@commander-hub`.
2. Start Codex and run `/hooks`.
3. Review the Commander entries (they run `node` scripts from the plugin directory) and trust them.
4. Start a new session. Hooks fire from then on.

Trust is bound to the hook definition, so repeat steps 2 and 3 after a plugin update that changes `hooks.json`. Until then skills still work; only hook-driven behavior (auto-routing, the what-next menu, session context, guards, telemetry) is absent.

Check: `/hooks` lists the Commander hooks as trusted. If none fire, the cause is almost always an untrusted definition, not a script error.

## Not verified here

- The trust flow and `request_user_input` rendering have not been exercised on a live Codex install; the tests check the hook's JSON output and the generated files only.
- Codex exposes no documented way to read trust status, so a `/ccc-doctor` check for untrusted hooks is a follow-up.
