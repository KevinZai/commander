# Dual-host hook contract (Claude Code + Codex)

One set of Node hook scripts and one `hooks/hooks.json` serve both hosts. This page records the contract and the Codex trust step. Slice 1 of CC-2064: documentation only, no runtime change. Platform facts: [platform-facts-2026-10.md](platform-facts-2026-10.md) §2.2 and §3.3.

## Contract

| Item | Rule |
|---|---|
| Source of truth | `commander/cowork-plugin/hooks/hooks.json` and `hooks/*.js`. The Codex copy under `commander/cowork-plugin-codex/` is generated by `npm run build:codex`; never hand-edit it. |
| Command form | Quoted shell form: `node "${CLAUDE_PLUGIN_ROOT}/hooks/x.js"`. Codex has no `args` exec form. Desktop installs sit under a path with a space, so the quotes are required. |
| Plugin root | Codex sets `PLUGIN_ROOT` and `PLUGIN_DATA`, plus `CLAUDE_PLUGIN_ROOT` / `CLAUDE_PLUGIN_DATA` as compatibility aliases. Claude Code sets only the `CLAUDE_*` pair. `${CLAUDE_PLUGIN_ROOT}` therefore resolves on both hosts and is never rewritten. |
| Manifest | `.codex-plugin/plugin.json` declares `"hooks": "./hooks.json"` and `extensions.com.openai.hooks`; the Claude plugin loads `hooks/hooks.json` by convention. |
| Events | Codex supports 12 events. Claude-only events are dropped from the mirror (`commander/adapters/codex/hook-event-map.json`). |
| Handler fields | Codex lacks `args`, `onFailure`, `if`, `once`, and skips `async` handlers. Translation strips `async` and keeps the timeout so the handler still runs, synchronously. SessionEnd timeout stays at 3 s. |
| Host detection | A hook that must behave differently checks `process.env.PLUGIN_ROOT`: set means Codex, unset means Claude Code. Example: `hooks/orchestrator/session-start-orchestrator.js` omits `watchPaths` on Codex because Codex has no FileChanged hook. |
| Menus | Claude Code uses `AskUserQuestion` chips. Codex has no such tool, so skills fall back to a one-line numbered prompt. `commander/adapters/codex/ask-bridge.js` is experimental and not wired. |

A new hook is dual-host if it: uses the quoted command form, reads only the common input fields (`session_id`, `cwd`, `hook_event_name`, `transcript_path`), emits only output fields both hosts accept, and branches on `PLUGIN_ROOT` for anything host-specific.

## Codex one-time hook trust

Installing or enabling the plugin does not trust its hooks. Codex skips plugin-bundled hooks until the user reviews and trusts the current hook definition. No adapter can bypass this, and Commander does not try to.

Onboarding text for Codex users:

1. Install: `codex plugin marketplace add KevinZai/commander`, then `codex plugin add commander@commander-hub`.
2. Start Codex and run `/hooks`.
3. Review the Commander entries (they run `node` scripts from the plugin directory) and trust them.
4. Restart the session. Hooks fire from the next session on.

Re-approval: trust is bound to the hook definition, so after a plugin update that changes `hooks.json`, repeat steps 2 to 3. Until then, skills still work; only hook-driven behavior (session context, guards, telemetry) is absent.

Verify: `/hooks` lists the Commander hooks as trusted. If none fire, the cause is almost always an untrusted definition, not a script error.
